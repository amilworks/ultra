- 2026-06-09 Streamed-text ordering fix (out-of-order live deltas under multi-replica fanout): User reported the live event stream rendered garbled/scrambled prose while a run was solving, even though the persisted final message was clean — a decisive clue that the defect is in the live delivery path, not the model. Traced it: the V2 run-event SSE handler (`streamRunEvents` in `internal/httpapi/handlers.go`) wrote each event arriving on the control plane's local in-memory bus *directly* to the client, then relied on a 1s periodic store catch-up to fill anything missing. Under the multi-replica design the event-ingest NATS consumer is a queue group shared across replicas, so a streaming client connected to replica A receives only the delta batches A happened to ingest on its local bus; batches ingested by replica B reach A's SSE only via the slower store catch-up. The old code therefore emitted a late delta (e.g. sequence 50, locally fanned out) *before* the earlier sequences 45–49 (ingested elsewhere) that the catch-up delivered a beat later — scrambling streamed text in arrival order while the store stayed correctly sequenced, which is why the final render was clean. Reproduced with a TDD backend test (`TestRunEventsStreamDeliversSequenceOrderWhenBusCarriesPartialEvents`): persist deltas 1–5 to the shared store, fan out only the last on the local bus, and assert the SSE body carries strictly increasing sequences 1..6 with no gaps — it failed (delivered seq 6 with 2–5 missing until catch-up), then passed after the fix. Fix: treat a local-bus event as a wake-up signal and deliver from the store in sequence order (skip bus events at/below the cursor; on any newer bus event run the same ordered `catchUpFromStore` used by the periodic ticker) so deltas always flush in order regardless of which replica ingested them. Hardened the client to match: `consumeV2RunEventStream` now drops run events whose sequence is ≤ the last seen (replay/reconnect overlap no longer doubles streamed text — `skips duplicate run event sequences...` test), and the live run-events poll in App.tsx now fetches incrementally from a sequence cursor and accumulates instead of re-paging from zero every 1.25s tick (`getRunEvents`/`listRunEvents` gained an `afterSequence` option; tests `fetches run events incrementally...` and the chat-slice delegation test). Live verification on the exact two-replica topology (replicas :18080/:18081 on shared Postgres+NATS, browser proxied to A): a fresh long run that emits a numbered 1–25 list rendered in strict monotonic order in the DOM through the whole stream (sampled repeatedly; the only "decrease" was the model deliberately starting a second complexity-sorted enumeration, confirmed by the store containing two enumerations), and the reconstructed store first pass was exactly 1..N. Gates: `go test ./...` green, frontend `pnpm test:unit` 346/346, `pnpm typecheck` and `pnpm lint` clean, no streaming/ordering console errors. Labeled separate minor finding (out of scope for this fix): the figure/thumbnail render path emits a React "empty string passed to src" warning when an image URL is momentarily empty — pre-existing, unrelated to streaming, to be addressed separately.
